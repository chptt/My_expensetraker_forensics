# Security assumptions and limitations

This document states what DailySpend assumes about its environment, which behaviours the brief
prohibits, how each prohibition is enforced in code rather than in prose, and where the remaining
gaps are.

## 1. Assumptions

- **Authorisation.** The app is run only by a student on a device or emulator they control, inside a
  course lab network, for the purpose of producing and interpreting forensic artefacts.
- **Data provenance.** All financial content is either typed by the user or generated by the fixed
  fixture script. The repository contains no real personal or financial records. The course AVD does
  carry genuine call-log content, because the examiner acquires the provider database directly
  (see [docs/device-data-acquisition.md](device-data-acquisition.md)); that data reaches the
  evidence set without ever passing through this app, and every permission claim below is a claim
  about the APK, not about the lab host driving `adb`.
- **Trust boundary.** The only outbound network destination is the lab base URL configured on the
  Settings screen. The app has no other socket, no push channel, no analytics, no ad SDK, and no
  third-party backend.
- **Build posture.** Debug builds carry `LAB_DEFAULT_BASE_URL = http://10.0.2.2:5000/`,
  `LAB_ALLOWED_HOSTS = 10.0.2.2, localhost, 127.0.0.1` and `usesCleartextTraffic=true`. Release
  builds set the base URL and host allowlist to empty strings and `usesCleartextTraffic=false`.
  `LAB_ENABLED_BY_DEFAULT` is `false` in both.
- **Server availability.** Nothing in the tracker requires the Flask server; the lab module degrades
  to local-only logging when it is absent.

## 2. Prohibitions and how each is enforced

| Prohibition from the brief | Enforcement in this codebase |
| --- | --- |
| Do not hide the launcher icon | One exported `MainActivity` with the `MAIN`/`LAUNCHER` filter in `AndroidManifest.xml`; no activity-alias, no `enabled=false` toggle, no dynamic component switching |
| Do not misrepresent requested permissions | The debug manifest declares two permissions and comments each one where it is declared: `INTERNET` (lab transfers only) and `POST_NOTIFICATIONS` (the app's own lab-result notification). The ordinary expense features need neither, and the release manifest merger removes `POST_NOTIFICATIONS` because the release build strips the endpoint. `aapt2 dump xmltree` on both shipped APKs confirms debug = INTERNET + POST_NOTIFICATIONS, release = INTERNET |
| No real SMS, contacts, call logs, passwords or tokens | No `READ_SMS`/`READ_CONTACTS`/`READ_CALL_LOG`/`WRITE_CALL_LOG`/`READ_PHONE_STATE` permission (they could not be used without it), no `Telephony`/`ContactsContract`/`AccountManager`/`ClipboardManager` references anywhere in `app/src/main`, and no `CallLog.Calls` query or insert. The call-log rows the lab transmits are constants in `lab/SyntheticCallLogFactory.kt` under reserved `+91-90000-` numbers, and `ProcessedRecordStore` stores only fixture ids - never a device identifier |
| No exfiltration of actual call history | Three independent gates: `SyntheticCallLogFactory.isSynthetic()` requires the `syn-call-` id namespace, the `SYNTHETIC_LAB` source tag and both numbers inside the reserved block; `LabCallLogPayloadBuilder.build()` refuses the whole batch if any record fails it; `OkHttpLabApiClient.ingestSyntheticCallLogs()` re-checks every record and returns `InvalidPayload` before opening a socket. The lab server mirrors the check and refuses with 400 without storing the values. `SyntheticCallLogFactoryTest` and `OkHttpLabApiClientTest` assert a real-shaped number is refused at all three layers. Where the course needs genuine call history, the examiner acquires it from outside the app over `adb` - see [device-data-acquisition.md](device-data-acquisition.md) |
| No keystroke or clipboard capture | Input is collected by Material 3 `OutlinedTextField` in the app's own Compose screens only; no `EditText` focus listeners, no accessibility service, no clipboard API |
| No covert audio/video capture | No `RECORD_AUDIO`/`CAMERA` permission, no `MediaRecorder`/`CameraX` usage |
| No reading other apps' private data | No root calls, no `File()` paths outside the app's own `filesDir`/`getSharedPreferences`, no `ContentProvider` queries; `WRITE_TEST_MARKER` can only write inside `filesDir/lab_events` |
| No harvesting the notification tray | The security test posts **its own** notification through `NotificationManager` and archives the text it posted. There is no `NotificationListenerService`, no `android.permission.BIND_NOTIFICATION_LISTENER_SERVICE`, no declared `<service>` at all, and no read of another package's notifications anywhere in the project. `POST_NOTIFICATIONS` is the only notification permission, it is asked for solely from the **Allow lab result notifications** button on Settings while the lab switch is on - never at startup - and while it is outstanding `AndroidLabResultNotifier` reports `posted=false` so the archived row admits no tray entry was shown |
| No exfiltration of actual expense records | `LabPayloadBuilder.build()` accepts only `SyntheticExpenseRecord`, re-checks the `syn-` id and `Lab fixture - ` description markers, and `OkHttpLabApiClient.ingestSyntheticEvents()` re-checks every record before serialising. `AppContainer` never hands `expenseRepository` to the lab module, and the `expenses` table is not read by any lab class |
| No installing additional APKs | No `PackageManager` install requests, no `FileProvider` share of an APK, no downloaded bytes are ever written as a `.apk`; there is no code path that writes an executable file |
| No executing arbitrary server-supplied commands | `LabCommand` is a closed enum of four values; `LabCommandParser.validate` rejects unknown names, non-empty `parameters`, missing `issued_at_utc` and commands when no session is active, and execution is a `when` over the enum. No `Runtime.exec`, no `ProcessBuilder`, no `ScriptEngine`, no dynamic dex/class loading |
| No accessibility services monitoring other apps | No `<service>` element and no `android.accessibilityservice` metadata in the manifest or sources |
| No covert persistence, stealth or anti-analysis evasion | No `WorkManager`, `JobScheduler`, `AlarmManager`, `Service`, `BroadcastReceiver`, `BOOT_COMPLETED` hook, foreground service or thread that outlives the visible screen. Every lab action starts either from a button press on Settings or from the user saving a **new** expense while the lab switch is visibly on; the expense hook returns immediately when the switch is off, and both routes write their outcome to the visible log rather than acting quietly. There is no obfuscation tuned to hide lab behaviour, no log suppression, no root/emulator detection, no anti-debug checks. Release builds additionally strip the endpoint so nothing can talk to the lab at all |
| Retries only when the user opted in | `LabSessionManager.transferSyntheticBatch()` retries only when `config.retryEnabled && config.maxRetries > 0`; `retryEnabled` is a Settings switch persisted in `daily_spend_lab.xml` |
| Bounded logs, no tamper-proof claims | `ForensicEventLog` caps 500 records and 256 KB with one rotation file and truncates `detail` to 240 chars. The class comment, the README and the experiment guide all state plainly that these are ordinary app-private files |
| Feature-flagged server integration | `LabConfig.labEnabled` gates `OkHttpLabApiClient.ready()`; when it is off, every call returns `LabApiResult.Disabled` before a socket is opened, and Settings buttons are disabled. `LAB_ENABLED_BY_DEFAULT=false`, so the flag starts off in every build |

Unit tests lock these guarantees down: `LabPayloadBuilderTest` and `SyntheticExpenseFactoryTest` prove
real-shaped records are refused; `SyntheticCallLogFactoryTest` and `LabCallLogSyncTest` do the same for
the call-log fixtures and prove the switch-off path writes nothing at all;
`LabCommandParserTest` proves `SHELL`, `rm -rf /`, `READ_SMS`,
`UPLOAD_CONTACTS` and `INSTALL_APK` are rejected; `OkHttpLabApiClientTest` proves the feature flag
sends zero requests on all five endpoints and that a non-fixture batch aborts before touching the
server; `LabSessionManagerTest` proves retry only happens with the explicit switch and that the marker
file can only land inside the lab directory.

## 3. Cleartext HTTP: risk and containment

**Risk.** Plain HTTP transmits payloads that anyone on the path can read and modify. Even though the
bodies are synthetic, an attacker on the lab network could inject a hostile command response.

**Containment in this project.**
- Cleartext is allowed only in debug builds (`manifestPlaceholders["allowCleartextHttp"]`) and only
  for hosts listed by the build: `10.0.2.2`, `localhost`, `127.0.0.1`. `LabEndpointPolicy` refuses
  `http://` to any other host, refuses non-HTTP(S) schemes, and refuses hostless or malformed URLs.
  Release builds have an empty allowlist, so cleartext to any host is refused and the default base
  URL is blank.
- Command responses are validated against the four-item allowlist before anything happens, and the
  client ignores `parameters` entirely, so a tampered response cannot smuggle arguments.
- Responses are parsed as typed JSON; unparseable bodies become `InvalidPayload`, never an action.
- A production deployment of this pattern would require TLS with certificate validation and pinning,
  an authenticated session, and server-side authorisation of which session ids may receive commands.
  None of that is implemented here because the exercise is confined to an isolated emulator network.

## 4. Residual limitations (state these in any report)

1. **Not tamper-proof, not tamper-evident.** The JSONL log, the `security_lab_events` table and the
   preference file are all writable by the app and by anyone with root or `run-as` on a debug build.
   There is no hash chain, no signing, no remote attestation and no secure clock.
2. **Truncation and rotation are lossy.** Records older than the 500-line / 256 KB cap are dropped
   and only one previous file is retained.
3. **`readAll()` skips malformed lines.** A crashed or partially written final line is invisible to
   the parser while still present in the bytes; count records from the raw file.
4. **Clocks.** Every timestamp is device wall-clock time. Emulators are frequently out of sync, and
   there is no server-time reconciliation.
5. **The instrumentation suite is red.** It ran once, on a Genymotion Android 11 device on
   2026-10-15: all 18 Compose UI assertions failed on selector problems in the test code
   (unmerged-tree nav icons, below-the-fold `assertIsDisplayed()`, ambiguous price nodes). The app
   itself installed, launched and rendered. The JVM suite (165 tests, debug and release variants)
   does pass, and it is the one that encodes the security guarantees. The device test for the
   security-test notification compiles but has not been executed.
6. **No anti-tampering on the APK.** Debug builds are debuggable by design so that acquisition works;
   signature checks would be trivially bypassed and are out of scope. The release APK is signed with
   the local **debug** key so the course artifact installs - it is not an authorship claim and must
   not ship that way.
7. **The server is out of scope, and nothing has proven the APK-to-server leg.** No Flask
   implementation ships with this repository. The copy running on the lab host now answers all five
   documented routes correctly - verified over HTTP from the host on 2026-10-15, including the
   call-log route's accept/duplicate/refuse behaviour - but that verification was curl and Flask's own
   test client, not the installed app, so no APK-to-server delivery has been observed end to end. The
   Genymotion virtual device was not reachable when the work was done (`adb devices` listed nothing).
   See [server-integration.md](server-integration.md) §5.
8. **Single activity, single user.** The app has no authentication, no multi-user isolation and no
   encryption at rest beyond whatever the device provides (Android file-level encryption on the
   emulator's data partition). An acquired `daily_spend.db` from a powered-off, locked device is
   readable only insofar as the device itself is accessible.
9. **Backup surface.** Both `res/xml/backup_rules.xml` and `res/xml/data_extraction_rules.xml` list
   only `daily_spend.db`, so the expense database follows Android's normal backup rules while the
   lab artefacts under `files/lab_events` never leave the device. That is a design choice made for
   this exercise, not a general security recommendation.
10. **Synthetic call-log rows can be mistaken for recovered history.** This is the sharpest
    interpretation trap in the exercise. The `SYNTHETIC_CALLLOG_SYNC` payloads and the server's
    `synthetic_call_logs` table contain caller/callee numbers, directions, call types and durations in
    exactly the shape a real exfiltration artefact has - and they are all invented. Report them as
    fixtures or not at all, and cite the evidence that makes them identifiable: the reserved
    `+91-90000-` block, the `syn-call-` id namespace, `source: SYNTHETIC_LAB`, the fixed
    `2026-10-12` dates, and the manifest's lack of any call-log permission.
11. **The expense hook is a real behaviour change.** Saving a new expense while the lab switch is on
    now performs a network POST. That is the point of the exercise, but it means the ordinary
    tracker's timing is not identical to the lab module's being off: with the server unreachable the
    save still succeeds and the POST fails into `TRANSFER_FAILURE`, and the sync is serialised so a
    second save during an in-flight batch is refused rather than queued. There is still no
    background worker, so an unsent batch waits for the next app interaction.

## 5. If this were hardened for a real deployment

- TLS only, with certificate pinning and a server allowlist enforced at build time.
- Signed, append-only audit records (hash chaining or a write-once sink outside the app).
- Server-side authorisation, session binding, replay protection and command nonce.
- Removal of the ability to clear lab artefacts from inside the app.
- Independent verification that no permission is declared beyond what a feature actually uses.

## 6. Statement of purpose

The app exists to give students a convincing, self-contained set of artefacts to acquire and
interpret: a plausible everyday application, an opt-in module that looks suspicious in a log, and a
network channel that is deliberately incapable of becoming a remote-control channel. It is a forensic
experiment, not a deployable surveillance tool, and the enforcement table above is the reason it
stays that way.
